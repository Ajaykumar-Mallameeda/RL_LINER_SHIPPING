# Assumptions

**Status:** FROZEN
**Version:** 0.1
**Date:** 2026-09-12

Each assumption is tagged with its evidence basis:

- **CONFIRMED** — Directly supported by source
- **INFERRED** — Reasonable interpretation, not explicitly stated
- **PENDING VERIFICATION** — Requires further investigation

## Network Assumptions

| # | Assumption | Tag | Rationale |
|---|-----------|-----|-----------|
| N1 | The graph is directed: for each port pair (p,q), both (p,q) and (q,p) edges exist if the distance data includes both directions. | CONFIRMED | `dist_sparse.csv` contains bidirectional entries (e.g., PABLB→PAONX and PAONX→PABLB). |
| N2 | Service legs must connect ports that have a defined distance in the data. A service cannot include a leg between two ports without a distance entry. | INFERRED | The paper's edge features include distance; undefined distances would break the model. This is a safety constraint, not explicitly stated. |
| N3 | The maximum number of services \|S\| equals the total number of vessel classes times the maximum vessels of any class, but is effectively bounded by practical considerations. The exact value used in the paper is NOT specified. | PENDING VERIFICATION | Paper defines D_e = 6 + \|S\| but does not state the value of \|S\| per instance. |
| N4 | Services are cyclic (round-trip): the last port in the sequence connects back to the first port. | CONFIRMED | LINERLIB benchmark solutions show cyclic rotations; paper terminology "rotation" implies cycle. |
| N5 | Multi-loop services (butterfly services) are decomposed into simple services for evaluation purposes. | CONFIRMED | Paper Section 6 states: "we decompose all multi-loop services, such as butterfly services, into simple services." |

## Vessel Assumptions

| # | Assumption | Tag | Rationale |
|---|-----------|-----|-----------|
| V1 | Vessels sail exclusively at their design speed. No slow-steaming optimization is performed. | CONFIRMED | Paper Appendix A.3: "vessels operate strictly at their designed speed." |
| V2 | Fractional vessel assignments are allowed (e.g., 2.14 vessels of class 450). The paper explicitly allows and uses fractional values in cost calculations. | CONFIRMED | Paper Table 8 shows fractional counts (24.11, 2.03, etc.); Appendix A.3 states "allows for fractional vessel assignments." |
| V3 | Each vessel spends 1 day idle at each port call (in addition to sailing time). | CONFIRMED | Paper Eq. 35: "1 · v_fi" term per port per vessel; readme states "required 1 day at each port." |
| V4 | The number of vessels required for a service is calculated as: tour_distance / design_speed / 7 (weeks), using the fractional value directly — no ceiling is applied. Fleet-constraint enforcement (fractional vs. integer comparison against v_n) is NOT specified in the paper's extracted text. | PENDING VERIFICATION | Paper Appendix A.3: "allows for fractional vessel assignments, the required number of vessels can be calculated as a function of the total distance of the service and the vessel's designed speed." Table 8 confirms fractional values are used in cost calculations. However, whether the fleet constraint (sum of n_{v,s} ≤ v_n) is checked with fractional or integer values is unstated. |
| V5 | A vessel class can be assigned to multiple services simultaneously, subject to the quantity constraint. | CONFIRMED | Implicit in the fleet data structure where each class has a total quantity available. |

## Demand Assumptions

| # | Assumption | Tag | Rationale |
|---|-----------|-----|-----------|
| DM1 | Demand is expressed in FFE (Forty-foot Equivalent units) per week. | CONFIRMED | Column header "FFEPerWeek" in demand files. |
| DM2 | Revenue_1 represents revenue per FFE shipped (not total revenue). | CONFIRMED | Paper Eq. 29: R_total = Σ_d d_R · (routed quantity), where d_R = Revenue_1. |
| DM3 | Each origin-destination pair represents a single commodity. Multiple demands between the same OD pair are aggregated into one commodity. | INFERRED | The MCF algorithm (Algorithm 1) iterates over demands d, suggesting each row is one commodity. If multiple rows share the same OD pair, they should be merged. |
| DM4 | Transit time constraints (TransitTime column) are NOT enforced by the MCF heuristic in the paper's implementation. | PENDING VERIFICATION | The paper's MCF (Algorithm 1) sorts by revenue and uses handling cost as edge weight, with no explicit transit time check. However, the transittime_revision files suggest transit time matters for instance validity. |

## Routing Assumptions

| # | Assumption | Tag | Rationale |
|---|-----------|-----|-----------|
| R1 | Cargo may be transshipped at any port between any two services. | CONFIRMED | Transshipment cost p_t is defined per port in ports.csv; MCF expanded graph (Fig. 4) models transshipment. |
| R2 | Transshipment incurs a per-FFE cost (p_t) but no capacity constraint. | CONFIRMED | Expanded graph shows transshipment proxy edges with infinite capacity. |
| R3 | Cargo loaded on a service can only be offloaded at a port visited by that service. | CONFIRMED | By definition of the network flow model. |
| R4 | The MCF heuristic processes demands in descending order of revenue per FFE. | CONFIRMED | Algorithm 1, line 3: "Descending sort D based on R." |
| R5 | For each demand, the heuristic finds the least-cost path using Dijkstra's algorithm on the expanded graph, where edge weights represent marginal handling costs. | CONFIRMED | Appendix B, following Algorithm 1. |

## MCF Assumptions

| # | Assumption | Tag | Rationale |
|---|-----------|-----|-----------|
| M1 | The MCF is a greedy heuristic, NOT an optimal solver. It may produce suboptimal flow assignments. | CONFIRMED | Paper explicitly calls it a "heuristic-based" approach and acknowledges it "lags behind MIP-based solutions." |
| M2 | The expanded graph representation (Fig. 4) is used for MCF evaluation, with proxy nodes for loading, offloading, and transshipment at each port. | CONFIRMED | Appendix B, Figure 4, Algorithm 1. |
| M3 | Path capacity is the minimum edge capacity along the path (bottleneck capacity). | CONFIRMED | Algorithm 1, line 9. |
| M4 | After routing a quantity q along a path, remaining capacities of all edges on that path are reduced by q. | CONFIRMED | Algorithm 1, lines 12-13. |
| M5 | The MCF is re-executed from scratch at every MDP step to compute the current network profit. | CONFIRMED | Algorithm 2: "Execute Algorithm 1 with current services S* on D" at each step. |
| M6 | The MCF is implemented independently (not shared with the GA/MILP system). | ENGINEERING DECISION | Required for repository independence; will be written in Python. |

## RL Assumptions

| # | Assumption | Tag | Rationale |
|---|-----------|-----|-----------|
| RL1 | The GAT encoder processes port features and edge features together through message passing. | CONFIRMED | Paper Section 4, Eqs. 7-9. |
| RL2 | The Transformer encoder receives both port embeddings and vessel embeddings as input. | CONFIRMED | Paper Eq. 11. |
| RL3 | No positional embeddings are used in the Transformer, as the graph structure has no inherent temporal ordering. | CONFIRMED | Paper Section 4: "We omitted the positional embedding layer." |
| RL4 | In the encoder-only approach, vessel selection is rule-based (not learned by the policy). | CONFIRMED | Paper Section 4 describes rule-based selection for encoder-only; neural selection only for encoder-decoder. |
| RL5 | In the encoder-decoder approach, vessel selection is part of the autoregressive decoding process. | CONFIRMED | Paper Section 4, Eqs. 15-27. |
| RL6 | The BOS (begin-of-service) embedding is randomly initialized and remains fixed throughout training and inference. | CONFIRMED | Paper Eq. 17 and surrounding text. |
| RL7 | Reward normalization divides by η₁ (profit after the first service), not η₀ (which is 0 for an empty network). | INFERRED | If η₀ = 0, normalization by η₀ would be undefined. The paper's use of η₁ implies the first step always produces positive profit. |
